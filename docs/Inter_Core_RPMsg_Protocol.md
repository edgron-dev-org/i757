# Inter-Core RPMsg Protocol (mbus Endpoint op Table)

> This document = the **sole authoritative contract** for the CM7↔CM4 application-layer payload (peer to `Backplane_Bus_Protocol.md`).
> The four underlying layers (HSEM doorbell / SRAM4 shared memory / vring queues / RPMsg endpoints) = standard components, not defined here; for integration and pitfalls see
> `platform_nucleo/Common/openamp/Integration_Guide.md`; this document governs only "what is written on the letterhead".
> Modification discipline: **any change to the op table must be synchronized into this document**; new ops take numbers starting from 0x0F (0x0C~0x0E and 0x11~0x13 are taken); 0x41~0x48 are already occupied by the backplane slave OTA (to avoid semantic confusion, they are not reused inter-core).

## 1. General Rules

- Endpoint: `"mbus"`, announced by CM4 (remote), bound by CM7 (host). One endpoint serves many services; the first payload byte = op opcode.
- Mode: except op6, everything is a **synchronous transaction** — CM7 sends the request and pumps messages in place waiting for the response, returning 0 on timeout; CM4 processes it on the dedicated rpc thread upon receipt and responds.
- Concurrency contract: on the CM7 side **any task may call `app_rpc_transact`** (mqtt / mbtcp / CLI / pimage), serialised by an internal mutex — **not** defaultTask-only ([2026-07-19] erratum: the old "single defaultTask thread" wording is obsolete); **on the CM4 side send/receive lives in a dedicated rpc thread** [2026-07-19] — the op1/op0A pass-through performs a real bus transaction inside the callback and blocks until the reply or the timeout, which would stall on-board sampling and the watchdog feed if it ran in the main loop. That thread is CM4's only caller of OpenAMP (both send and receive), so it is still zero-concurrency; it is serialised against the per-bus threads by a **per-bus mutex taken inside the leaf transaction functions**.
- Timeout: must be > 2× the CM4 tick + the business time; a Modbus transaction includes the bus round trip, currently ≥120ms.
- Payload limit: RPMSG_BUFFER_SIZE=512 − 16 (RPMsg header) = 496 bytes.
- Multi-byte integers are always **little-endian** (distinguished from the big-endian Modbus register values: that is an internal matter of the op1 payload and the bus contract).

## 3. Heartbeat and Health Criteria

- CM7 sends one `"hb"` every 5s (via echo, 30ms timeout) — **any** response refreshes `s_last_rx`.
- `app_rpc_alive()` = received any reply within 15s; it is one of the OTA trial-period promotion criteria (cloud_ok && rpc_alive).
- op6 has no response, so it **does not feed alive** — the health criterion recognizes only round trips.

## 4. Design-Decision Memos

- **op byte vs one endpoint per service**: the orthodox RPMsg approach is to demultiplex via multiple named endpoints (on the Linux side, one endpoint per device node). The current single endpoint + op byte = the simplest transaction model; if a Linux main controller joins, it is recommended to split the high-frequency service (op1) into its own endpoint, while the remaining ops-and-maintenance ops can stay.
- **op1 payload = untouched Modbus PDU**: the business semantics remain the standard protocol; the op layer only does sorting — the actual scope of "custom" is just miscellaneous ops-and-maintenance.
- Three survival disciplines (hard-won): ① transact-entry guard (reject sending when the endpoint is unbound; sending to an empty endpoint = HardFault); ② pump once before sending to clear a leftover response and prevent misalignment; ③ the hot-reset race is cured at the root by wiping the resource table before CM7 wakes CM4 (integration guide appendix).
